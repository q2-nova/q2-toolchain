# X2000 MSA and scalar instruction costs

Historical measurement on the Q2 on 2026-11-18 with `tests/perf/msa_microbench.py`
(program `tests/perf/msa_microbench/msa_bench.c`). All numbers are from the
Q2 at 1.2 GHz (`scaling_cur_freq` 1200000, governor `performance`, read
before, during and after every run), on CPU 0, beside the paused installed
player. Emulator runs check only that the program executes and that scalar
and MSA kernels give identical output.

Use: choose instructions and layouts for hand-written MSA from the tables and
the [rules](#rules-for-hand-written-msa-on-the-x2000); the
[LLVM section](#inputs-for-an-llvm-cost-model) lists the same costs in the
form a cost model needs.

## Method

- **Loops.** Each benchmark is one inline-asm loop: 64 or 96 copies of the
  instruction, then `addiu`, `bnez`, `nop`. The tail adds 1.5 cycles per
  iteration when it is not hidden behind a longer chain, so 0.508 in the
  tables means 0.50 cycles and 1.016 means 1.00.
- **Variants.**
  - *Latency:* one chain, each result feeds the next instruction.
  - *4, 8, 12 chains:* that many independent chains, interleaved.
  - *Independent:* 12 destinations, sources never written.
  - *Accumulator:* for `wd = wd op (ws, wt)` instructions, one chain through
    `wd` only.
  - *Throughput:* the lowest of the 4, 8, 12 and independent columns, in
    cycles per instruction. For `sqrt.s`, `sqrt.d`, `fsqrt`, `frsqrt` it is
    the independent column, because their chains settle at 1.0, which this
    core computes faster than other values.
- **Time.** `clock_gettime(CLOCK_MONOTONIC)` around about 5 ms of iterations
  (the clock steps in 167 ns), 5 repetitions, minimum; then the minimum over
  5 runs of the program. Cycles = ns × 1.2. In the reported session 5 of 860
  values were reached by only one run; a 3-run session 3 minutes earlier
  agrees within 3% on all but 8 values (all loads or single outliers).
- **Cycle counter.** `rdhwr $2` (CC) executes in user mode without a trap
  (2.7 ns per read) and reports resolution 1, but the value does not
  advance (0 ticks in 20 ms). It is not usable.
- **Values.** Integer chains run on small integers. Float chains run on
  normal values (1.5, 1.25, 1.37) unless the row says otherwise; conversion
  chains run on 0.0, with a second row on a non-zero value.
- **Memory.** Instruction tests use one zeroed 16 KiB buffer (L1-resident;
  L1D is 32 KiB, 8-way, 32-byte lines; L2 is 512 KiB, 64-byte lines). Load
  and store rows touch 12 addresses 32 bytes apart unless they say "one
  address".
- **Kernels.** 1024 elements per pass over 4 KiB buffers, scalar code written
  per element in dependency order, 4 elements per loop iteration. Every
  scalar/MSA pair produced identical output (FNV checksum of the output
  buffer) on the Q2 and in the emulator.
- **Run time.** One run takes 31–39 s on the Q2. The 5-run session held the
  device lease for 164 s, a 3-run session for 109 s.
- **Not measured:** branch misprediction penalty as a number, L2 load
  latency, power, the second core, other clock frequencies, MSA instructions
  absent from the table, and which loops of the player slowed down in the
  MSA-everywhere build.

## Core

| Property | Measured |
| --- | --- |
| Issue width | 2 instructions per cycle (`nop`, `addu`, `and`, `sll`, `slt`: 0.50 cycles each) |
| Scalar integer latency | 1 cycle; `mul` 3; `movn` 1 with throughput 1 per cycle; `div`+`mflo` about 22 |
| Scalar load | `lw` latency 3 (pointer chase); 1 load per cycle from different lines, 2 per cycle from one address |
| Scalar store | 1 per cycle to one address, 1 per 2 cycles to 12 different lines; `sw` then `lw` of the same address 6.0 cycles |
| MSA issue | 2 per cycle for add, subtract, saturating add, average, min, max, compare, `move.v`, `mulv.b`; 1.67 per cycle for `mulv.h/w`, `maddv`, `dotp_s.h`; 1.6 per cycle for `fadd.w`, `fmul.w`, `addv.d`; 1 per cycle for logic, shifts, saturate, shuffles, interleave, pack, conversions, `fill`, `copy_s`, `insert`, `ldi` |
| MSA latency | 3 cycles for integer add, logic, shift, compare, min/max, saturate, shuffle, interleave, pack; 2 for `move.v`, `splati`, `sldi`, `insve`, `insert`, `fmax`, `fmin`, `fcle`, `fclt`; 4 for `mulv.h/w`, `maddv`, `dotp_s.h`, `addv.d`; 5 for conversions and `dotp_s.w`, `dpadd_s.w/d` |
| Lane-serial MSA instructions | `fdiv.w` 60 cycles (scalar `div.s` 15), `fdiv.d` 56 (`div.d` 28), `div_s.w` 66, `fsqrt.w` 56 (`sqrt.s` 14), `fsqrt.d` 56 (`sqrt.d` 28), `fmul.d` 4.0 (`mul.d` 2.0), `fadd.d` 2.0 (`add.d` 1.0), `fmadd.d` 8.0, `mulv.d` 4.0 |
| Denormal operands | No trap. `fadd.w`/`add.s` 3 cycles as for normal values; `fmul.w`/`mul.s` 4 instead of 3; with `MSACSR.FS=1` `fmul.w` is 3 |

## What this says about the MSA-everywhere build

The questions about building everything with MSA (q2-player
[`docs/target-build.md`](https://github.com/q2-nova/q2-player/blob/main/docs/target-build.md#msa-code)):

- **128-bit operations issued as two halves:** no for integer `.b/.h/.w` and
  float `.w` (`addv.w` 0.50 cycles, `fadd.w` and `fmul.w` 0.625, the same as
  `add.s` and `mul.s`). Yes in effect for f64 and i64 multiplies and for
  every divide and square root: per lane they cost what the scalar
  instruction costs, with 1–3 cycles more latency.
- **Shuffles and widening:** not slow. Every shuffle, interleave and pack is
  1 per cycle with latency 3.
- **GPR↔vector moves:** 7 cycles for a round trip, 1 per cycle each way.
- **Unaligned loads:** 1.5 cycles instead of 1.0 at any address that is not
  16-byte aligned, 2.0 across a 32-byte line, 3.0 across a page. Stores cost
  the same aligned or not, except across a line (3.1 against 2.0).
- **FP latency:** `.w` 3 cycles, equal to scalar; `fadd.d` 6 against 5,
  `fmul.d` 7 against 5, `fmadd.d` 12 against 9.
- **Latency of cheap operations:** every MSA integer operation has latency 3
  where the scalar one has 1. A loop whose iterations depend on each other
  through such an operation runs at a third of the scalar rate per step.

In all seven kernels here the best MSA version is 4 to 16 times faster than
the scalar code, so the MSA unit is not slow at straight-line pixel or sample work.

The MSA-everywhere binary has 10,283 instructions on MSA registers. Counted by
mnemonic: `copy_s.w` 2,137, `insert.w` 1,052, `copy_s.b` 198, `copy_s.h` 175,
`fill.w` 132; all `copy_s`, `copy_u`, `insert` and `fill` together 3,717 (36%
are GPR↔vector moves); vector loads 1,363 and vector stores 118; `sll.d` 433,
`srl.d` 432, `addv.d` 341, `or.v` 488, `xor.v` 485 (64-bit integer work in
vector registers). The measured costs fit a build that moves scalars in and out
of vectors: each crossing costs 3.5 cycles and each vector step 3 or 4 cycles
where the scalar instruction takes 1. Which functions these are, and which of
them caused the image and UI slowdown, is not measured. Recorded in `9cdb66bdc`
(2026-11-18).

The V0.93 EQ leaf uses `v2f64`. Per lane, `fmul.d` and `fadd.d` cost the
same as `mul.d` and `add.d` and have more latency, so its measured gain is
not explained by these instruction costs. Not investigated.

## Rules for hand-written MSA on the X2000

Each rule cites the numbers it comes from.

**Cheap**

- Integer add, subtract, saturating add/subtract, rounding average, min,
  max, compare on `.b/.h/.w`: 0.50 cycles, latency 3.
- `mulv.h`, `mulv.w`, `maddv.h/w`, `dotp_s.h`, `dpadd_s.h`, `mul_q.h`:
  0.60 cycles, latency 4. `mulv.b`: 0.50, latency 3.
- `fadd.w`, `fsub.w`, `fmul.w`: 0.625 cycles, latency 3.
- Logic, shifts, `sat_s`/`sat_u`, `bsel.v`, every `ilv*`, `pck*`, `shf`,
  `vshf`, `splati`, `sldi`: 1.0 cycle, latency 3 (2 for `splati`, `sldi`).
  Shuffles are not a reason to change a layout.
- Conversions (`ffint`, `ftint`, `ftrunc`, `fexdo`, `fexupr`, `ffqr`, `ftq`,
  `frint`): 1.0 cycle, latency 5.
- Aligned `ld`: 1.0 cycle, 0.56 when consecutive loads hit the same line.

**Avoid**

- Divide and square root in vectors: `fdiv.w` 60, `fdiv.d` 56, `div_s.w` 66,
  `frcp.w` 60, `fsqrt.w` up to 56, `frsqrt.w` up to 119 cycles. Multiply by
  a reciprocal computed once.
- f64 and i64 lanes for throughput: `fmul.d` 4.0, `fadd.d` 2.0, `fmadd.d`
  8.0, `mulv.d` 4.0 cycles per instruction (2 lanes). Per lane that equals
  scalar. Use f32 lanes where the arithmetic allows it.
- `fmadd.w`/`fmadd.d` in an accumulation: the accumulator path is 7 cycles
  (`.w`) or 12 (`.d`). `fmul.w` then `fadd.w` puts 3 cycles on the
  accumulator path and matches unfused scalar code. `fmadd.w` (0.875
  cycles) beats `fmul.w` + `fadd.w` (1.25) only with 8 accumulators.
- GPR↔vector moves inside a loop: `fill.w` + `copy_s.w` is 7 cycles. Keep
  loop counters and pointers in GPRs and data in vectors; load constants and
  splats before the loop.
- Reloading what was just stored: `st.w` → `ld.w` 12 cycles, `st.w` → `lw`
  about 10 (13 with `fill.w`). Extract with `copy_s`, not through the stack.
- A loop-carried dependency through one MSA instruction per element (running
  sums, IIR state, pixel filters that use the previous output): 3 cycles per
  step against 1 for scalar integer code. Vectorize across independent
  streams (rows, channels) or leave it scalar.
- `pref`: copying with `pref` 256 bytes ahead is slower at every size
  (6,891 against 10,800 MiB/s at 16 KiB, 489 against 980 MiB/s at 8 MiB).
- Loads that are not 16-byte aligned when alignment is free: 1.5 cycles
  against 1.0, and the 16 KiB sum drops from 14,192 to 8,972 MiB/s. Unaligned
  loads are still cheaper than any scalar alternative.
- Stores scattered over many lines: 2.0 cycles each against 1.0–1.2 for
  sequential output.

**Accumulators (independent chains)**

| Reduction | Latency | Chains needed |
| --- | --- | --- |
| Integer add, min, max on `.b/.h/.w`, register operands | 3 | 8 (0.75 cycles at 4, 0.50 at 8) |
| The same with one `ld` per step | 3 | 4: loads limit the loop to about 1 vector per cycle (sum over 16 KiB: 5.1 cycles per 4 vectors) |
| `maddv.h/w`, `dpadd_s.h` | 4 | 8 (1.0 at 4, 0.60 at 8) |
| `dpadd_s.w`, `dpadd_s.d` | 5 | 8 (1.25 at 4, 1.0 at 8) |
| `fadd.w` | 3 | 8 (1.0 at 4, 0.625 at 8); 4 when each step also has a load or `fmul.w` |
| `fmadd.w` | 7 | 8 (1.75 at 4, 0.875 at 8) |
| `fadd.d` | 6 | 4 (2.0 at 4, 8 and 12) |
| `fmadd.d` | 12 | 2 (8.0 at 4, 8 and 12) |

More than 8 chains gained nothing in any row.

**Audio (f32, i32, i16)**

- Keep stereo interleaved for per-sample work (gain, conversion, clamping):
  one `ld.w`/`st.w` handles 2 frames with no shuffle. Split channels with
  `pckev.w`/`pckod.w` or `ilvev.w`/`ilvod.w` (1.0 cycle, latency 3) only
  when the channels need different coefficients.
- Use f32 lanes. A `v2f64` vector gives no per-lane gain over scalar f64.
- Allocate sample buffers 16-byte aligned and process in place or to a
  sequential output.
- i16 → f32: `ffqr.w`/`ffql.w`, 0.56 cycles per sample (interleave, shift,
  `ffint_s.w`, `fmul.w`: 1.75; scalar: 5.02).
- f32 → i32 with scale and saturation: `fmul.w` + `ftint_s.w`, 1.50 cycles
  per sample (scalar 7.01).
- i32 → i16 with saturation: `sat_s.w` + `pckev.h`, 0.89 cycles per sample
  (scalar conditional moves 6.5, branches 8.0 predictable and 14.2 when half
  the samples clip).
- Sums of products: i16 input with `dpadd_s.w` or `maddv.h`, i32 input with
  `maddv.w`, 4 accumulators with loads; f32 with `fmul.w` + `fadd.w`.

**Pixels (RGBA and RGB u8)**

- RGBA/RGBX, 4 pixels per vector, rows 16-byte aligned: no shuffle is
  needed for per-channel work. Byte operations that exist directly
  (`adds_u.b`, `subs_u.b`, `aver_u.b`, `min_u.b`, `max_u.b`) are 0.50 cycles
  per 16 bytes.
- Multiplies: widen with `ilvr.b`/`ilvl.b` against a zero register, `mulv.h`,
  `srli.h`, `pckev.b`: 0.94 cycles per byte (scalar 4.51).
- u8 → f32: `ilvr/ilvl.b`, `ilvr/ilvl.h` with zero, `ffint_u.w`: 0.88 cycles
  per element (scalar 3.52). f32 → u8 with saturation: `ftrunc_s.w`,
  `maxi_s.w`, `sat_u.w`, two `pckev`: 2.57 (scalar 16.4).
- RGB24: convert to RGBA once at the boundary with `vshf.b` (1.27 cycles per
  pixel, scalar 6.17), then work on RGBA. The 12-byte step makes every load
  unaligned (1.5–2.0 cycles) and each 16-byte load reads 4 bytes past the
  4 pixels it converts; the last load of a buffer needs those bytes to exist.
- `vshf.b` overwrites its control register: one `move.v` per shuffle (the
  pair is 3.0 cycles as a chain, and 3.0 per pair at 4 chains).

**Start-up cost**

- A thread's first MSA instruction costs 1.7 µs, and the first FP or MSA
  instruction after each context switch 1.5 µs. A kernel that saves less
  than about 2,000 cycles per call in a thread that otherwise uses no FP
  does not pay for itself.

**Copies**

- For L1- and L2-resident data an `ld.b`/`st.b` loop copies at 10,800
  MiB/s (16 KiB) and 2,659 MiB/s (256 KiB); libc `memcpy` reaches 2,891 and
  978 MiB/s. At 8 MiB the copies without `pref` are within 13% of each other
  (870–980 MiB/s).

### Where the defaults are likely wrong for this core

- Vector register width 32 and interleave factor 1 hide the two measured
  facts that make MSA pay: 128-bit operations at scalar throughput, and
  reductions that need 4–8 chains.
- Insert and extract at cost 1 understate a crossing that puts 3.5 cycles on
  the dependency path. The MSA-everywhere binary contains 3,717 such moves
  in 10,283 MSA instructions.
- Float arithmetic at a flat 2 per vector overstates v4f32 (1.25 relative to
  `addu`) and understates v2f64 (`fadd` 4, `fmul` 8, `fmuladd` 16), which
  has no per-lane gain over scalar.
- v2i64 `mul` (8) and every vector divide (112–132) are priced as ordinary
  legal operations.
- Shuffles priced as N inserts and extracts overstate the one-instruction
  patterns by 8 to 32 times.
- Latency is absent from the vectorizer's throughput costs: a recurrence
  through an MSA operation costs 3 cycles per step, 1 in scalar integer
  code.
- Unaligned vector loads (1.5) and line-crossing loads (2.0) cost the same
  as aligned ones in the default.
- The generic scheduling model gives MSA logic and shuffles latency 1 and
  adds latency 2 (measured 3), issue width 1 (measured 2), and one latency
  for `.w` and `.d` float operations (measured 3 against 6–7).
